# MechaCore 库文件移植与重构分析报告

## 1. 整体架构对比
- **core (MechaCore)**: 现代化的 C++ 框架。采用分层设计（HAL -> BSP -> Alg -> APP），大量使用命名空间、模板类和回调机制。具有很强的解耦性和可扩展性。
- **当前项目 (Dart)**: 典型的 C-Style 结构，但在部分逻辑（如 MotorObject）中已经开始尝试对象化。代码中存在较多全局变量和硬编码逻辑。

---

## 2. 适合且易于移植的模块 (推荐)

### 🟡 Alg (算法层) - **移植难度：低 | 价值：极高**
- **包含模块**：`PID`, `Filter`, `ADRC`, `Slope`, `UtilityFunction`
- **分析**：
    - **纯数学实现**：这些库不调用任何硬件接口，完全独立。
    - **精度优势**：`core` 里的 PID 使用 `float` 运算，支持积分限幅、积分分离、微分先行等现代特性，远优于当前项目中的 `PID_Speed_Temp`。
    - **接口友好**：采用 `Update(target, feedback)` 模式，非常容易集成进现有的 `MotorObject` 中。

### 🟢 BSP (板级支持包) - **移植难度：中 | 价值：高**
- **包含模块**：`RemoteControl (DT7)`, `Common/StateWatch`
- **分析**：
    - **DT7**：核心解析逻辑非常标准且稳定。通过 `StateWatch` 统一管理遥控器掉线检测，比当前在各个任务里零散检查要更专业。
    - **StateWatch**：这是一套通用的状态监控工具，只要在循环或回调中调用其时间更新函数，就能统一处理所有传感器/电机的掉线报警。

---

## 3. 适合移植但需要硬件适配的模块 (进阶)

### 🟢 BSP/Motor (电机驱动) - **移植难度：中 | 风险：CAN层依赖**
- **模块**：`DjiMotor` 模板类
- **分析**：
    - **优势**：完美解决了单位换算问题（RPM, Deg, Rad）和多电机管理。
    - **适配点**：它深度绑定了 `core/HAL/CAN` 的发送接口。如果要用，建议连同 `core/HAL/CAN` 一起移植，或者为它写一个适配器。

### 🔵 HAL (硬件抽象层) - **移植难度：中 | 风险：环境冲突**
- **模块**：`CAN`, `UART`, `LOGGER`
- **分析**：
    - **优势**：提供了优雅的回调机制（Callback），不再需要在 `main.c` 里的 `RxCpltCallback` 写大篇幅的 `if`。
    - **适配点**：需要确保 `impl` (实现层) 里的句柄名称（如 `hcan1`, `huart6`）与 CubeMX 生成的一致。如果当前项目已经占用了这些中断回调，可能会冲突。

---

## 4. 可能出现兼容性问题的模块 (谨慎)

### 🔵 HAL/DWT (计时器) 
- **风险**：如果项目使用了不同的底层计时（如使用了 `osDelay` 与 `HAL_Delay` 混合），可能会影响 DWT 延迟的准确性。

### 🟡 MatLab 生成代码
- **风险**：`core/MatLab/PullingForce` 等是针对特定机械数学模型生成的。如果 Dart 机器人的拉簧连杆机构或材料参数与生成代码时的物理模型不符，这些库会输出错误结果。

---

## 5. 重构建议路线

### 第一阶段：算法现代化 (Low Cost)
将 `core/Alg/PID` 引入，更新 `MotorControl.hpp` 中的 `MotorObject`，使其持有此 PID 对象。
- **收益**：消除整数截断误差，PID 调参更容易。

### 第二阶段：状态监控统一化 (Mid Cost)
引入 `core/BSP/Common/StateWatch`。
- **收益**：将电机掉线检测、遥控器连接检测统一在一个框架下，不再需要手动在 `RegularEvent` 里重复写计时逻辑。

### 第三阶段：全架构切换 (High Cost)
将 `APP_Task` 以外的所有逻辑废弃，全面使用 `core` 下的 `HAL` 和 `BSP`。
- **收益**：代码极度整洁，未来新增其他兵种代码时复用率极高。
